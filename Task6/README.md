# Задание 6. Движок классификации данных

Диаграмма C2 движка классификации: [Draw.io](classification-engine-c2.drawio).

## Поток обработки

1. Оркестратор принимает пакет из CRM, лаборатории, 1С или файлового импорта, фиксирует источник, версию и контрольную сумму и сохраняет payload в зашифрованный временный буфер с коротким retention.
2. Schema Detector сравнивает структуру со Schema Registry. Профилировщику передаются схема и минимально необходимая выборка, а не отдельная неуправляемая копия пакета.
3. Data Profiler определяет типы, статистики, шаблоны ПДн и медицинскую лексику без сохранения исходных значений в логах.
4. Rule Engine и ML Classifier независимо предлагают класс и теги. Policy Engine объединяет результаты и учитывает оценку уверенности.
5. Неизвестные поля и результаты ниже порога уверенности отправляются в зашифрованный Quarantine. Review UI получает только авторизованный маскированный preview; Data Steward подтверждает или исправляет класс, после чего версионированное правило попадает в реестр.
6. Protection Service получает из временного буфера сам payload и отдельно — утверждённые теги. Затем применяет токенизацию, маскирование, удаление лишних полей и получает data key из KMS.
7. Данные и метаданные загружаются в нужный слой хранилища; все решения фиксируются в Audit & Metrics.

## Слои аналитического хранилища

| Слой | Назначение | Доступ и защита |
|---|---|---|
| Quarantine | Неизвестная схема, низкая уверенность, ошибки | Только Data Steward и безопасность; шифрование отдельным ключом; короткий retention |
| Restricted Raw | Минимально необходимая исходная копия для воспроизводимости | Сервисные аккаунты; отдельные ключи по доменам; аудит каждой операции |
| Protected Curated | Нормализованные и размеченные данные | Токенизация прямых идентификаторов, маскирование, ABAC по цели |
| Anonymized Marts | BI/ML/AI без необходимости знать пациента | Агрегация, обезличивание, контроль риска повторной идентификации |
| Metadata Catalog | Схемы, теги, lineage, владельцы и retention | Доступ аналитиков к метаданным без доступа к значениям |

Временный encrypted buffer внутри движка не является аналитическим Raw-слоем: он нужен только для атомарной пакетной обработки и удаляется после подтверждённой загрузки либо истечения короткого TTL. Постоянный исходный набор, если он действительно необходим для воспроизводимости, хранится только в `Restricted Raw`.

## Метрики качества

| Метрика | Зачем нужна |
|---|---|
| Precision по каждому классу | Показывает долю корректных срабатываний и помогает не завышать класс без причины |
| Recall по `STRICT` и `CONFIDENTIAL` | Главная метрика безопасности: показывает, сколько чувствительных полей найдено |
| F1-score по классу | Балансирует precision и recall при сравнении версий правил и модели |
| False negative rate для `STRICT` | Используется как блокирующий критерий выпуска новой версии классификатора |
| Доля записей в карантине | Выявляет неподдержанные схемы и слишком строгие пороги |
| Доля ручных исправлений | Показывает, какие правила или признаки нужно доработать |
| Schema drift rate | Позволяет заранее увидеть изменения источников |
| Throughput и p95 времени пакета | Подтверждают, что движок справляется с ростом объёма |
| Доля ошибок загрузки и повторов | Показывает устойчивость и корректность идемпотентной обработки |

Для production фиксируются пороги: `Recall STRICT >= 0,99`, `False Negative Rate STRICT <= 0,01`, отсутствие необработанных schema drift, контролируемая доля карантина и производительность не ниже пятикратного прогнозного профиля. Точные p95 и throughput утверждаются после замера базового объёма; релиз блокируется при ухудшении recall/FNR относительно утверждённого контрольного набора.

Для оптимизации я сравниваю версии правил и модели на размеченном контрольном наборе. Новая версия включается постепенно; при ухудшении recall класса `STRICT` выполняется автоматический откат.

## Масштабирование

- Пакеты разбиваются на независимые партиции и передаются через очередь.
- Stateless-компоненты классификации масштабируются горизонтально в Kubernetes.
- Rule Engine применяется первым как быстрый и объяснимый этап; ML вызывается для неоднозначных полей.
- Schema Registry, каталог и хранилище используют версионирование, репликацию и партиционирование по источнику/дате.
- Backpressure ограничивает приём новых пакетов при перегрузке, а DLQ изолирует ошибочные сообщения.
- Кэш правил и моделей снижает задержку; метрики очереди управляют автоскейлингом.
- Добавление нового источника выполняется через конфигурацию адаптера и схему без изменения ядра классификатора.
